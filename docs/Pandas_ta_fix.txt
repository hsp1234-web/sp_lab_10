「pandas-ta-openbb」技術分析函式庫版本穩定化報告

執行摘要


「赫爾墨斯計畫」目前面臨著 pandas-ta 技術分析函式庫與最新 NumPy 2.0 版本之間嚴重的相容性問題。原始 pandas-ta (版本 0.3.14b) 已過時，且缺乏對 NumPy 2.0 的官方支援，其長期可行性亦明確表示不確定。
本報告主要建議採用 pandas-ta-openbb，這是一個活躍維護的分支，專為 NumPy 2.0 相容性而設計，並已整合至更廣泛的 OpenBB 金融生態系統中。此分支不僅解決了即時的相容性問題，也為「赫爾墨斯計畫」的技術分析需求提供了一個更穩健、更活躍開發的途徑。
擬議方案的主要優勢：
* 確保 NumPy 2.0 相容性，解決關鍵的執行時錯誤。
* 取得活躍維護且功能增強的技術分析函式庫。
* 與 OpenBB 平台對齊，可能帶來未來的整合效益。
* 為「赫爾墨斯計畫」的量化分析奠定穩定且具備未來擴展性的基礎。

1. 緒論：「赫爾墨斯計畫」的技術分析基礎




1.1. 技術分析在「赫爾墨斯計畫」中的作用


技術分析是「赫爾墨斯計畫」量化能力的基石，為市場趨勢識別、訊號生成和風險管理提供必要的指標。這些指標的準確性和可靠性對於計畫的成功至關重要。所選的技術分析函式庫必須提供全面的功能、易於整合，並且最重要的是，具備與核心資料科學堆疊的長期穩定性和相容性。任何潛在的技術中斷都可能對計畫的運營效率和分析結果的可靠性產生重大影響。


1.2. pandas-ta 概述及其重要性


pandas-ta (Pandas Technical Analysis) 是一個 Python 函式庫，透過超過 130 個技術指標和實用功能擴展了 Pandas DataFrame 1。它設計易於使用，提供多種處理風格，包括標準、DataFrame 擴展和基於策略的方法 1。該函式庫的受歡迎程度源於其廣泛的功能集、與 TA-Lib 的相關性測試，以及與 Pandas DataFrames 的整合，使其非常適合以資料為中心的金融分析工作流程 1。
pandas-ta 的安裝過程透過 pip 即可輕鬆完成 1。此外，該函式庫還支援建立自訂策略和指標鏈結，這對於開發複雜的交易演算法和自訂分析方法至關重要 1。其靈活性和豐富的功能使其成為量化金融領域中廣泛採用的工具。


1.3. 挑戰：numpy 2.0 相容性


NumPy 2.0 的近期發布引入了對其 API 和 ABI 的重大破壞性變更 7。這些變更是基礎性的，可能導致依賴 NumPy 的函式庫（如
pandas-ta）出現執行時錯誤或非預期行為。對於「赫爾墨斯計畫」而言，目標不僅是解決這些即時的相容性問題，還要建立一個「長期、穩定」的技術分析函式庫版本。這需要一個活躍維護且能夠應對不斷發展的 Python 生態系統依賴關係的解決方案。未能解決這些相容性問題將直接影響計畫的穩定性、可維護性和未來的擴展能力。

2. 相容性現況深度解析




2.1. numpy 2.0：理解破壞性變更


NumPy 2.0 是一個主要版本，引入了對 Python 和 C API 的向後不相容變更 7。這些變更對於未來的效能改進、資料類型處理和更廣泛的生態系統對齊是必要的。
主要破壞性變更包括：
* np.NaN 移除： 一個直接且常見的 AttributeError 來源是 np.NaN (大寫) 被移除，取而代之的是 np.nan (小寫) 8。這是一個直接的 API 變更，若不處理將立即導致程式失敗。
* 類型提升規則： NumPy 資料類型提升規則的變更意味著涉及不同浮點精度的操作（例如 np.float32 + Python float）現在可能返回較低精度的結果，或行為與 NumPy 1.x 不同 9。在金融計算中，精度至關重要，這種變化可能悄悄地改變技術指標的值，潛在地影響交易策略或回測結果。這表示即使
pandas-ta 在基本修復後能夠執行而沒有明確錯誤，其輸出結果也可能與先前版本有細微的差異或不正確，需要進行廣泛的重新驗證。
* 命名空間清理： np 主命名空間中約有 100 個成員已被棄用、移除或移至子模組 8。這包括
np.float_ (應使用 np.float64) 和 np.Inf (應使用 np.inf) 等別名 8。
* C-API 變更： 對 C-API 的重大變更，包括 PyArray_Descr 結構和複雜類型處理，影響了在較低層次與 NumPy 介面的函式庫 8。這對於
pandas-ta 中可能使用 numba 或直接 C 擴展的效能關鍵部分尤其重要。
* nan_to_num 行為： 雖然 np.nan 是標準用法，但 np.nan_to_num 11 仍然將 NaN 替換為零或使用者定義的值，並將無限大替換為大的有限數。此函數的核心行為保持一致，但 NaN 的來源可能受到其他類型提升變更的影響。
值得注意的是，NumPy 專門提供了一個 Ruff 規則 (NPY201) 以自動適應這些變更 9。如果
NumPy 認為有必要提供自動化的 linting/修復工具來處理這些變更，這意味著這些破壞性變更在大型程式碼庫中是廣泛且難以手動處理的。這進一步證實了修補原始 pandas-ta 將是一項艱鉅且容易出錯的任務。因此，依賴一個已經完成此複雜遷移的社群維護分支（例如 pandas-ta-openbb）是一種更穩健且高效的策略。這利用了專業化的努力來解決系統性的生態系統挑戰，為「赫爾墨斯計畫」確保了更大的長期穩定性。


2.2. pandas-ta (原始版本) 的現況


pandas-ta 在 PyPI 上的最新官方版本為 0.3.14b，發布於 2021 年 7 月 28 日 2。這表明該函式庫缺乏近期更新。該專案的「關於攪動 (About Churn)」部分，如
pandas-ta-openbb 描述中所引述 12，指出：「該函式庫的狀態及其緩慢的版本增長似乎正在影響其長期可行性和支援。這種從 Intercooler JS 改編而來的變體闡明了
Pandas TA 為何沒有頻繁版本更新。這並非因為它已死，而是因為它（大部分）是正確的：基本思想是正確的，且實作至少足夠正確。因此，專案不會有持續的活動和攪動，而是一種管理關係，主要目標是不搞砸。文件和測試將得到改進，功能/指標將根據需要添加/移除，但不會有大規模的重寫或持續更新。這與通常具有滑稽程度攪動的軟體行業形成對比。」
然而，同一部分 12 也包含一個嚴峻的警告：「儘管使用指標顯示，當前和過去的支援水準不足以維持和改進該函式庫。除非在 2026 年 7 月 1 日之前獲得顯著的額外支援，否則這個廣泛使用的函式庫將被封存。」這種說法在專案哲學與現實可行性之間造成了顯著的矛盾。雖然該專案聲稱處於穩定、「大部分正確」的狀態，但明確威脅因缺乏支援而將函式庫封存，這表明維護和長期可行性存在關鍵的潛在問題。這種哲學立場似乎是為不活躍找藉口，而非穩健、成熟穩定的標誌。對於需要「長期、穩定」函式庫的「赫爾墨斯計畫」而言，依賴原始
pandas-ta 是一個高風險的選擇。其緩慢攪動的哲學被專案可能被封存的真實威脅所掩蓋，這將導致大量的技術債務和近期潛在的平台重構工作。這使得原始函式庫從根本上不適合計畫的長期目標。
此外，其 GitHub 儲存庫 (twopirllc/pandas-ta) 顯示有限的開放問題和拉取請求，表明 main 分支上的活躍開發最少 13。


2.3. pandas 與 numpy 2.0 相容性


pandas 本身已經解決了 NumPy 2.0 的相容性問題。Pandas 2.2.2 (發布於 2024 年 4 月) 是第一個與 NumPy 2.0 大致相容的版本 16。這意味著
pandas 2.2.2 及更高版本設計為可與 NumPy 1.x 和 NumPy 2.x 協同工作 17。
存在一個注意事項：使用 NumPy 2.0 新的 StringDtype 建立的陣列，在 Series/DataFrame 建立時將轉換為 object 資料類型陣列。對 StringDtype 的全面支援預計將在 pandas 3.0 中實現 17。這不太可能直接影響
pandas-ta 的數值計算，但對於更廣泛的資料處理值得注意。Python 社群的普遍看法是，儘管 NumPy 2.0 引入了破壞性變更，但 pandas 已進行了適應，並且生態系統正在朝著相容性方向發展 16。
pandas 與 NumPy 2.0 相容是一個關鍵資訊。pandas-ta 顧名思義，與 pandas 深度整合。如果 pandas 本身已成功渡過 NumPy 2.0 的轉換期，這意味著底層資料結構和核心操作是相容的。這降低了 pandas-ta（或其分支）實現 NumPy 2.0 相容性的複雜性，因為它不必在 NumPy 的基礎上處理根本的 pandas 不相容問題。這種生態系統的對齊證明了尋找一個與 NumPy 2.0 協同工作的 pandas-ta 解決方案是可行的。這表明主要挑戰在於 pandas-ta 直接的 NumPy 呼叫和內部邏輯，而不是源於 pandas 本身的一系列不相容問題。這為可以實現並維護相容的 pandas-ta 版本提供了信心。

3. 解決方案分析：pandas-ta-openbb 分支




3.1. pandas-ta-openbb 的介紹與目的


pandas-ta-openbb 是原始 pandas-ta 函式庫的一個獨立分支，其建立的明確目的就是「為了分發與 NumPy 2 相容的 wheel」12。這直接解決了「赫爾墨斯計畫」的核心相容性問題。它基於原始
pandas-ta 的 develop 分支 12，這表明它包含了原始版本
0.3.14b 發布後可能存在的錯誤修復和改進。該分支由 pandas-ta 的同一作者 Kevin Johnson 維護 12，這表明專業知識的延續性。
原始 pandas-ta 專案明確表示可能因「不可持續的支援」而被封存 12。同時，
pandas-ta-openbb 是由同一作者 (Kevin Johnson) 為了 NumPy 2.0 相容性並與 OpenBB 整合而明確建立的分支 12。這表明作者做出了一項策略性決定，將開發和支援工作轉移到一個新的、更可行的管道（OpenBB 生態系統內的
pandas-ta-openbb），而不是試圖重振原始的、可能停滯的專案。原始專案的「關於攪動」聲明 12 可能是在為其現狀進行回溯性辯解，而該分支則代表了確保函式庫未來的積極舉措。這種開發重點的轉移意味著
pandas-ta-openbb 不僅僅是一個臨時修補程式，而是 pandas-ta 核心功能活躍開發的事實延續，特別是解決了 NumPy 2.0 等現代依賴要求。對於「赫爾墨斯計畫」而言，這個分支不僅是一個替代方案；它是函式庫演進和支援的預期長期路徑。


3.2. 功能與增強


pandas-ta-openbb 保留了 pandas-ta 的核心功能，提供超過 150 個指標和實用工具，以及 60 多個燭台模式（安裝 TA-Lib 後）12。它利用
numba 進行效能增強，這對於計算密集型金融分析至關重要 12。它提供了熟悉的 Pandas DataFrame 擴展「ta」，簡化了時間序列計算 12。該專案強調與 TA-Lib 和 TradingView 等其他流行平台的指標等效性 12。


3.3. 已確認的 numpy 2.0 相容性與活躍開發


pandas-ta-openbb 最重要的方面是其明確聲明與 NumPy 2.0 相容 12。這直接回應了「赫爾墨斯計畫」的即時挑戰。該分支顯示活躍開發，近期發布了 0.4.22 版本，時間為 2025 年 7 月 4 日 12。這與原始
pandas-ta 的停滯發布歷史形成鮮明對比。其 PyPI 下載統計數據顯示持續使用，每週/每月有數千次下載 18。


3.4. 在 OpenBB 平台內的整合


pandas-ta-openbb 是 OpenBB 平台不可或缺的一部分，OpenBB 是一個開源金融平台，提供對多樣化金融資料和廣泛擴展的存取 19。OpenBB 明確將
pandas-ta 列為一個擴展 19，並且
pandas-ta-openbb 的 PyPI 頁面證實其用於「與 NumPy 2 和 OpenBB 一起使用」12。
OpenBB 平台強調模組化、可擴展性和資料標準化 21，使
pandas-ta-openbb 成為一個更大、活躍開發的生態系統的一部分。OpenBB 的安裝過程可以透過 pip install openbb[all] 包含所有擴展 20。使用者對 OpenBB 的評價強調其易用性、Pandas 整合以及作為「開源版彭博終端」的潛力 23。
pandas-ta-openbb 與 OpenBB 平台明確相關 12。OpenBB 是一個全面、活躍開發的金融資料平台 20。這種整合意味著
pandas-ta-openbb 受益於更廣泛的 OpenBB 開發工作，包括測試、依賴管理和社群參與。它不是一個獨立的分支，而是更大、策略性專案的組成部分。這顯著增強了其長期穩定性和相關性，超越了僅僅是 NumPy 2.0 相容性。OpenBB 專案對開源金融工具的承諾 23 提供了堅實的基礎。透過採用
pandas-ta-openbb，「赫爾墨斯計畫」不僅解決了相容性問題；它還在策略上與一個充滿活力且不斷發展的金融科技生態系統對齊。這為其技術分析能力提供了更穩健和可持續的基礎，未來可能提供新的資料來源、分析工具和社群支援，遠超原始 pandas-ta 所能提供的。這直接滿足了「赫爾墨斯計畫」對「長期、穩定」的要求。

4. 「赫爾墨斯計畫」的策略性建議




4.1. 主要建議：採用 pandas-ta-openbb


理由：
   * 直接相容性： pandas-ta-openbb 明確解決了 NumPy 2.0 的相容性問題，這是「赫爾墨斯計畫」最直接且最關鍵的問題 12。
   * 活躍開發與維護： 與原始 pandas-ta 不同，openbb 分支活躍維護並有近期發布，確保持續的錯誤修復、效能改進和功能更新 12。這降低了函式庫過時或無人維護的風險。
   * 長期可行性： 其與 OpenBB 金融平台的整合為未來的支援和開發提供了穩健的生態系統，符合「赫爾墨斯計畫」對「長期、穩定」解決方案的需求 19。
   * 功能對等/增強： 它保留了原始 pandas-ta 的全面功能，同時透過 numba 增加了效能增強 12。


4.2. 遷移策略與實施步驟


   * 步驟 1：環境隔離： 優先為「赫爾墨斯計畫」的開發和部署使用隔離的 Python 環境（例如 venv、conda）或容器化（例如 Docker）。這對於精確的依賴管理和防止與其他系統級 Python 套件的衝突至關重要 16。
   * 步驟 2：安裝 pandas-ta-openbb： 使用該分支替換現有的 pandas-ta 安裝：
Bash
pip uninstall pandas-ta
pip install pandas-ta-openbb

（參考安裝說明 12）。
   * 步驟 3：更新 pandas 和 numpy： 確保 pandas 版本為 2.2.2 或更高，numpy 版本為 2.0.0 或更高。
Bash
pip install "pandas>=2.2.2" "numpy>=2.0.0"

（參考 Pandas 相容性 17）。
   * 步驟 4：程式碼審查與測試：
      * 對「赫爾墨斯計畫」現有的 pandas-ta 實作進行徹底的程式碼審查。雖然 API 大致一致，但由於 NumPy 的類型提升，可能會出現細微的行為變化 9。
      * 對所有技術分析組件實施全面的單元測試和整合測試，以根據已知良好值驗證輸出，尤其是在依賴升級之後。密切關注涉及 NaN 值和浮點精度計算的邊界情況。
      * 步驟 5：依賴文件更新： 更新 requirements.txt、pyproject.toml 或 conda 環境文件，明確鎖定 pandas-ta-openbb、pandas 和 numpy 的版本至已驗證的相容版本。


4.3. 穩健的依賴管理


      * 虛擬環境/容器化： 強制要求「赫爾墨斯計畫」的所有開發和生產部署使用虛擬環境（例如 venv、conda）或容器化（例如 Docker）16。這種做法隔離了專案依賴，防止衝突並確保不同機器和團隊成員之間的環境一致性。
      * 嚴格版本鎖定： 始終在 requirements.txt 或等效文件中鎖定關鍵函式庫（pandas-ta-openbb、pandas、numpy、numba、scipy、statsmodels）的精確版本 25。這確保了未來的安裝能夠重現確切的工作環境。
      * 自動化依賴掃描： 將自動化依賴掃描工具（例如 pip-audit、dependabot）整合到 CI/CD 管道中，以監控上游函式庫的安全漏洞和潛在的破壞性變更。
研究資料顯示，NumPy 2.0 引入了破壞性變更 7，
pandas 隨之進行了適應 17，而
pandas-ta-openbb 則專門為 NumPy 2.0 相容性而創建 12。然而，OpenBB 自己的範例需求有時仍顯示較舊的
numpy 和 pandas 版本 25。這表明即使在像 OpenBB 這樣的大型生態系統中，向
NumPy 等基礎函式庫的新主要版本過渡也是複雜且分階段進行的。雖然 pandas-ta-openbb 與 NumPy 2.0 相容，但更廣泛的 OpenBB 平台或其他範例的某些部分可能仍在較舊、穩定的 NumPy 1.x 堆疊上運行。這凸顯了在整個依賴圖中維護相容性的持續挑戰。因此，對於「赫爾墨斯計畫」而言，僅僅採用 pandas-ta-openbb 是不夠的。一個積極且嚴格的依賴管理策略，包括嚴格的版本鎖定和隔離環境，絕對是必要的。這種積極的方法確保「赫爾墨斯計畫」能夠維護其「穩定」的技術分析函式庫版本，無論更廣泛的 OpenBB 生態系統處於何種過渡狀態或未來發生何種變化。它有助於避免「依賴地獄」並確保可重現性。

問題根源：設計特性而非系統錯誤
感謝您提供的最新資訊！這是一個非常重要的突破。原來我們一直在追查的 .ta 擴充功能未在 Pandas Series 物件上註冊的問題，並非系統錯誤，而是 pandas-ta-openbb 函式庫的 「設計特性」。
這意味著：
         * pandas-ta-openbb 的 .ta 擴充功能只為 DataFrame (二維數據表) 註冊了功能，並未對 Series (一維數據序列) 進行註冊。
         * 我們之前在 Series 上嘗試使用 .ta 的所有努力，實際上都是與該函式庫的設計意圖相悖的。
________________


衝突的底層原理：使用者預期與函式庫設計的落差
這次遇到的問題並不是傳統意義上的「依賴項衝突」或「版本不相容」。它的底層原理更像是 「使用者對函式庫功能的預期」與「函式庫實際設計」之間的落差。
更具體來說：
         1. 使用者預期： 在像 pandas-ta 這樣的技術分析函式庫中，使用者很自然地會認為無論是單一股票的價格序列 (Series) 還是多支股票的價格數據表 (DataFrame)，都應該可以直接透過 .ta 擴充功能來計算指標。這符合直覺和常見的數據處理模式。
         2. 函式庫設計： 然而，pandas-ta-openbb 的作者可能基於某些設計考量（例如簡化內部邏輯、避免歧義或針對特定使用情境），選擇只在 DataFrame 層級上註冊 .ta 擴充功能。這代表他們預期使用者會將數據組織成 DataFrame 後再進行技術分析。
這種資訊不對稱，導致我們將其誤判為複雜的環境或依賴問題，並投入了大量時間進行偵錯。
________________


解決方案：調整使用方式以符合設計
既然我們已經明確了問題的根源是設計特性，那麼解決方案就變得非常直接和明確：
將您的數據在執行技術分析前，先確保其為 Pandas DataFrame 格式，然後再呼叫 .ta 擴充功能。
舉例來說，在您原來的 genesis_run.py 腳本中，price 變數是透過 vbt.YFData.download('SPY', ...).get('Close') 獲取的，這通常會返回一個 Pandas Series。
要解決這個問題，您只需要在呼叫 .ta 之前，將這個 Series 轉換為 DataFrame。
具體調整範例：
Python
import pandas as pd
import numpy as np
import vectorbt as vbt
# ... 其他導入 ...


print("--- [階段 1] 數據獲取 ---")
price = vbt.YFData.download('SPY', start='2020-01-01').get('Close')
print("✔ SPY 歷史價格數據已成功獲取。")


print("\n--- [階段 2] 特徵工程 (Feature Engineering) ---")


# **關鍵的修改點：將 Series 轉換為 DataFrame**
# 確保 price 是一個 DataFrame，這樣才能使用 .ta 擴充功能
# 可以選擇將 Series 命名為 'Close' 列，或者根據需求調整
price_df = pd.DataFrame(price) # 將 Series 轉換為 DataFrame
# 或者如果 price 已經是 Series 並且您想保留原始 Series 名稱作為列名
# price_df = price.to_frame()


# 現在在 DataFrame 上使用 .ta 擴充功能
price_df.ta.strategy("Momentum", append=True) # 現在這行應該能正常工作了！


features = price_df.iloc[:, 1:].copy() # 取得所有 ta 指標欄位
features.dropna(inplace=True)
print(f"✔ 已成功計算 {features.shape[1]} 個技術指標作為特徵。")
print("特徵預覽:")
print(features.head())
