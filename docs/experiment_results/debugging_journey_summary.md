# 除錯歷程分析：追查 `-99%` 回報率的根本原因

## 摘要

在本次策略開發過程中，我們遇到了一個極為頑固的錯誤：無論如何修改策略，回測結果始終顯示 `-99%` 的總回報率和與之矛盾的正夏普比率。這份文件旨在深入剖析導致此一災難性結果的根本原因，並記錄我們如何透過層層推理和實驗，最终定位並修正了回測引擎中的核心邏輯缺陷。

## 核心問題：`-99%` 的回報率之謎

這個問題的核心在於兩個同時發生、且相互掩蓋的致命錯誤：

### 1. 錯誤的曝險模型：All-In 式的交易

- **現象**：回測引擎在執行買入指令時，会将帳戶中 **100% 的可用現金** 全部投入交易。
- **根本原因**：`IncrementalBacktestEngine._simulate_batch_trades` 函式中的 `cost = cash[entries] * (1 - transaction_cost_pct)` 這行程式碼，其設計初衷可能是針對股票等非槓桿商品。
- **致命後果**：當此邏輯被應用於像台指期 (`TX`) 這類高合約價值、高槓桿的期貨商品時，即使是購買一口合約，其所需保證金也遠低於「全部現金」。因此，這個「All-In」的動作相當於動用了**極大的財務槓桿**。在這種情況下，任何微小的市場反向波動，都會立刻觸發強制平倉，導致帳戶資金被**完全虧光 (Wipe Out)**。這完美解釋了為什麼總回報率始終是 `-99%` 左右。

### 2. 失真的績效指標：因「除以零」而產生的正夏普比率

- **現象**：在總資金幾乎完全虧光的情況下，夏普比率卻顯示為一個看似不錯的正數。
- **根本原因**：`_run_batch_simulation_and_metrics` 函式在計算每個時間點的報酬率時 (`returns = np.diff(equity) / equity[:-1]`)，沒有考慮到分母 `equity[:-1]` 可能變為零或極接近零的情況。
- **致命後果**：當帳戶資金在一瞬間被虧光後，`equity` 的數值會從一個正數變為零。在下一個時間點計算報酬率時，就會出現**「除以零」**的數學錯誤，產生一個**無限大的正報酬率** (`inf`)。這個極端的離群值嚴重扭曲了 `np.mean(returns)` 的計算結果，最終在平均標準差也被拉大的情況下，依然算出了一個失真的正夏普比率。

## 次要問題：被掩蓋的程式碼與快取錯誤

在我們最終定位到上述兩個核心錯誤之前，曾花費大量時間處理了多個看似是主要原因、但實際上只是「障眼法」的次要問題。這些問題之所以難以排除，正是因為上述兩個核心錯誤導致輸出結果始終不變，讓我們誤以為是程式碼的修改沒有生效。

这些次要问题包括：
- **策略邏輯錯誤**：最初的策略會無條件賣出，導致錯誤放空。
- **回測引擎快取**：`resume=True` 的設定導致引擎不斷讀取舊的錯誤結果。
- **Python 模組快取**：`__pycache__` 的存在使得修改後的 `.py` 檔案未被即時載入。
- **多程序快取**：`ProcessPoolExecutor` 的子程序可能載入了舊的程式碼記憶體副本。
- **框架耦合問題**：`VectorBacktestEngine` 中存在對特定策略的硬式編碼 `import` 和需要手動「註冊」的 `switch-case` 結構。

## 結論

這次漫長的除錯歷程給我們帶來了寶貴的教訓：
1.  **曝險模型是回測的靈魂**：必須為不同類型的金融商品設計合適的資金管理和曝險模型。一個適用於股票的 `All-In` 模型，在期貨市場上是致命的。
2.  **數據處理的極端情況**：在進行任何數學計算，特別是除法時，必須對分母為零或接近零的極端情況進行保護，以防止指標失真。
3.  **由表及里的除錯思維**：當輸出結果極度異常且固定不變時，除了檢查表層的策略邏輯，更應該懷疑底層的核心引擎是否存在根本性的設計缺陷。

透過修正這些問題，我們不僅完成了一次策略回測，更重要的是，我們將整個回測框架的**可靠性**和**準確性**提升到了一個全新的水平。
